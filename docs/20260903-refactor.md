* read, grep 등은 core에 새 operation (build_file_context을 만들어) 이는 hook을 트리거하고 hashline은 그 훅에서 augment 하게 만들어줄 수 있어?
* freeform을 별도의 description을 쓸 수 있게 만들어서 prompts/tool_patch_hashline.txt 와 prompts/tool_patch_hashline_freeform.txt 를 나눠.
* write tool은 첫번째 줄에 path 그 아랫줄에 content를 작성하게 해.
* patch_hashline의 스키마는 json_schema 유틸을 써서 생성하게 해.
  * 하나의 큰 스키마로 퉁치지 말고 enum 형식으로 생성해.
  * 복잡한 conversion logic 대신 json을 그대로 쓸 수 있으면 좋을 것 같아.

=====
앞으로 operation에서 registry를 참고하는 일이 많아질 것 같아. 그렇다고 operation을 호출할 때마다 인자를 들고다니는 것도 좋아보이지 않아.
1. SessionHandle spawn을 (registry, store) 구조로 만들고 걔가 SessionRuntime을 만들어서 operation, registry, workdir을 SessionRuntime 소유로 붙이고
2. Operation은 runtime을 weak ref로 참조하고
3. TurnEngine은 SessionRuntime에서부터 생성하게 하고
하는 건 어때?

=====
# Airicode Runtime / Tool Rework Implementation Plan

## 1. 목적

이번 변경의 목적은 앞으로 core operation이 `Registry`, `Workdir`, session state/store/event 등 여러 runtime resource를 자연스럽게 사용할 수 있도록 실행 구조를 재정리하고, 그 위에서 파일 컨텍스트/hashline 및 tool input/freeform 처리를 단순화하는 것이다.

핵심 목표는 다음과 같다.

1. `SessionRuntime`을 세션 실행 환경의 단일 소유자로 만든다.
2. `Operations`는 `SessionRuntime`을 `Weak` reference로 참조하는 얇은 capability handle로 만든다.
3. `TurnEngine`은 `SessionRuntime`에서 생성되며 runtime을 `Arc`로 참조한다.
4. `read` / `grep`의 파일 표시 로직을 `build_file_context` operation으로 공통화한다.
5. hashline은 `read` / `grep` tool의 기능이 아니라 `build_file_context` hook augmentation으로 구현한다.
6. freeform tool은 JSON mode와 다른 description을 가질 수 있도록 한다.
7. `write` freeform 입력을 `첫 줄 path + 이후 content` 형식으로 단순화한다.
8. `patch_hashline` JSON schema를 `schemars`/`json_schema`와 Rust enum으로 생성한다.
9. 가능하면 `serde_json::Value`를 직접 파고드는 conversion logic을 제거하고 실제 입력 타입을 `Deserialize + JsonSchema`의 single source of truth로 사용한다.

---

## 2. 설계 원칙

### 2.1 SessionRuntime이 runtime dependency의 루트가 된다

현재 여러 실행 객체에 분산되어 있는 다음 dependency를 `SessionRuntime`으로 모은다.

- `Registry`
- `Workdir`
- `SessionStore`
- session actor sender / snapshot receiver
- runtime event sender
- session / group / project identity

향후 operation이 새로운 runtime resource를 필요로 하더라도 호출 인자에 dependency를 계속 추가하지 않는다.

### 2.2 Operations는 state owner가 아니라 capability handle이다

`Operations` 자체가 `Registry`, `Workdir`, sender 등을 각각 복제해 들고 다니지 않는다.

```rust
#[derive(Clone)]
pub struct Operations {
    runtime: Weak<SessionRuntime>,
}
```

operation 실행 시 runtime을 upgrade한다.

```rust
impl Operations {
    fn runtime(&self) -> Result<Arc<SessionRuntime>> {
        self.runtime
            .upgrade()
            .ok_or_else(|| Error::Session("session runtime is no longer available".into()))
    }
}
```

`Operations`가 runtime lifetime을 연장하지 않도록 `Weak`를 사용한다.

### 2.3 TurnEngine은 실행 중 runtime lifetime을 보장한다

`TurnEngine`은 turn 실행 중 runtime이 사라지지 않아야 하므로 strong reference를 가진다.

```rust
pub struct TurnEngine {
    runtime: Arc<SessionRuntime>,
}
```

권장 lifetime은 다음과 같다.

```text
SessionHandle ── Arc ──┐
                       ▼
                 SessionRuntime
                       ▲
TurnEngine ───── Arc ──┘

Operations ──── Weak ─ ─ ─▶ SessionRuntime
```

### 2.4 SessionRuntime은 Operations 인스턴스를 필드로 소유하지 않는다

다음과 같은 self-reference는 만들지 않는다.

```text
SessionRuntime
  └─ Operations
       └─ Weak<SessionRuntime>
```

strong cycle은 아니지만 `Arc::new_cyclic()` 같은 불필요한 초기화가 필요해진다.

대신 필요할 때 handle을 만든다.

```rust
impl SessionRuntime {
    pub fn operations(self: &Arc<Self>) -> Operations {
        Operations {
            runtime: Arc::downgrade(self),
        }
    }

    pub fn turn_engine(self: &Arc<Self>) -> TurnEngine {
        TurnEngine {
            runtime: self.clone(),
        }
    }
}
```

### 2.5 Workdir과 FileContext의 의미를 분리한다

- `Workdir::read()` = raw filesystem access
- `Operations::build_file_context()` = 모델/tool에 보여줄 파일 representation 생성

patch 구현이나 내부 파일 조작에서 `build_file_context()`를 raw read 대용으로 사용하지 않는다.

반대로 `read` / `grep`처럼 모델에게 파일 내용을 보여주는 tool에서는 가급적 `Workdir::read()`를 직접 호출하지 않는다.

```text
Core
 │
 ├─ Registry
 ├─ Project
 └─ create/open/load session
          │
          ▼
    SessionHandle
          │ Arc
          ▼
    SessionRuntime
      ├─ Registry
```

# 4. Phase 1 — SessionRuntime 도입

## 4.1 `SessionRuntime` 타입 추가

새 타입을 추가한다.

파일 구조는 다음 중 하나를 사용한다.

권장:

```text
src/core/runtime/
  mod.rs
  session_runtime.rs
  turn_engine.rs
```

변경량을 줄여야 한다면 우선:

```text
src/core/runtime.rs
src/core/session_runtime.rs
```

로 시작해도 된다.

예상 필드:

```rust
pub struct SessionRuntime {
    project_id: ProjectId,
    session_id: SessionId,
    group_id: SessionGroupId,

    registry: Registry,
    workdir: Arc<dyn Workdir>,
    store: Option<Arc<dyn SessionStore>>,

    sender: mpsc::Sender<SessionRequest>,
    snapshot: watch::Receiver<SessionState>,
    events: broadcast::Sender<RuntimeEvent>,
}
```

필드는 가능한 한 private 또는 `pub(crate)`로 유지하고 accessor를 제공한다.

예:

```rust
impl SessionRuntime {
    pub(crate) fn registry(&self) -> &Registry;
    pub(crate) fn workdir(&self) -> &dyn Workdir;
    pub(crate) fn session_id(&self) -> SessionId;
    pub(crate) fn group_id(&self) -> SessionGroupId;
    pub(crate) fn project_id(&self) -> ProjectId;
}
```

## 4.2 actor lifecycle을 SessionRuntime 생성 과정에 통합

현재 `SessionHandle::spawn*`에서 생성하는 다음 상태를 runtime 생성 과정으로 이동한다.

- `mpsc::channel`
- `watch::channel`
- `broadcast::channel`
- `run_actor()` spawn
- store 연결

`SessionHandle`은 actor resource를 각각 들고 있지 않고 `Arc<SessionRuntime>` 하나만 보유한다.

```rust
#[derive(Clone)]
pub struct SessionHandle {
    runtime: Arc<SessionRuntime>,
}
```

## 4.3 SessionHandle spawn signature 변경

현재처럼 state/store만으로 session을 만들지 않고 runtime dependency를 함께 전달한다.

목표 API 예시:

```rust
SessionHandle::spawn(
    state,
    registry,
    project,
    store,
)
```

또는 인자가 커지면 별도 deps struct를 둔다.

```rust
pub struct SessionRuntimeDeps {
    pub registry: Registry,
    pub project: Project,
    pub store: Option<Arc<dyn SessionStore>>,
}
```

```rust
SessionHandle::spawn(state, deps)
```

`(registry, store)`만 받는 형태는 피한다. 현재 `Workdir` 생성에는 project root와 workdir layering context가 필요하기 때문이다.

## 4.4 Workdir 생성 책임을 SessionRuntime으로 이동

SessionRuntime 생성 시:

1. project root 기반 base workdir 생성
2. `WorkdirLayerContext` 생성
3. `registry.layer_workdir()` 적용
4. 최종 layered workdir을 runtime에 저장

예상 흐름:

```text
Project.root
   ↓
NativeWorkdir
   ↓
registry.layer_workdir(...)
   ↓
Arc<dyn Workdir>
   ↓
SessionRuntime.workdir
```

이후 `Core`나 `TurnEngine`이 별도로 workdir을 전달하지 않는다.

## 4.5 Core session API migration

다음 API들을 새 spawn 경로로 이동한다.

- `Core::create_session`
- `Core::open_session`
- `Core::load_session`
- `Core::open_or_create_session`
- `new_session`
- `new_session_with_store`

가능하면 `new_session*` helper는 제거하거나 `SessionHandle::spawn`의 얇은 wrapper로 축소한다.

`Core`는 자신의 `registry`, `project`, `session_store`를 조합하여 runtime을 만든다.

# 5. Phase 2 — Operations를 Weak<SessionRuntime> handle로 변경

## 5.1 기존 Operations 필드 제거

```text
sender
session_id
group_id
events
```

대신:

```rust
pub struct Operations {
```

하나만 유지한다.

기존 operation들은 시작 시 runtime을 upgrade한 후 필요한 resource를 꺼낸다.

예:

```rust
pub async fn snapshot(&self) -> Result<SessionState> {
```

대상 예:

- emit event

## 5.3 Runtime resource accessor 정책

Operation 구현은 `SessionRuntime`의 `pub(crate)` accessor를 사용한다.

예:

```rust
runtime.registry()
runtime.workdir()
runtime.store()
runtime.events()
runtime.sender()
```

`SessionRuntime` field를 전부 public으로 열지는 않는다.

# 6. Phase 3 — TurnEngine을 SessionRuntime 기반으로 변경

## 6.1 TurnEngine 필드 축소

기존:

```rust
pub struct TurnEngine {
    pub registry: Registry,
    pub operations: Operations,
    pub workdir: Arc<dyn Workdir>,
```

변경:

```rust
pub struct TurnEngine {
    runtime: Arc<SessionRuntime>,
```

## 6.2 생성 경로 변경

기존 public constructor:

```rust
TurnEngine::new(registry, operations, workdir)
```

를 제거하거나 private으로 만든다.

대신:

```rust
session_handle.turn_engine()
```

또는:

```rust

```

를 사용한다.

이렇게 하면 서로 다른 session의 `Operations`와 `Workdir`/`Registry`를 실수로 조합할 수 없다.

## 6.3 TurnRequest에서 중복 identity 제거 검토

현재 `TurnRequest`가 다음 identity를 가진다면:

- `project_id`
- `session_group_id`
- `session_id`

이 값들은 runtime에서 이미 정해져 있으므로 request에서 제거하는 방향을 검토한다.

최종적으로 TurnRequest는 turn별 값만 갖는 것이 이상적이다.

```rust
pub struct TurnRequest {
    pub provider_id: ProviderId,
    pub model: String,
    pub mode: String,
    pub input: String,
    pub cancellation: CancellationToken,
}
```

단, 외부 API 호환성이나 session routing에 사용 중인 곳이 있으면 별도 migration 단계로 처리한다.

## 6.4 ToolContext 축소

현재 runtime과 중복되는 필드 제거를 목표로 한다.

최종 후보:

```rust
pub struct ToolContext {
    pub turn_id: TurnId,
    pub operations: Operations,
    pub cancellation: CancellationToken,
}
```

제거 후보:

- `project_id`
- `session_group_id`
- `session_id`
- `workdir`

필요한 정보는 operation/runtime accessor를 사용한다.

단, tool API에서 identity가 매우 자주 필요하고 operation 호출 없이 읽어야 한다면 identity만 유지하는 선택도 가능하다. `workdir`은 우선 제거하는 쪽을 권장한다.

# 7. Phase 4 — `build_file_context` operation 추가

## 7.1 목적

`read`와 `grep`이 직접 raw file을 읽고 표시 형식을 조립하지 않도록 한다.

`build_file_context`는 다음 역할을 담당한다.

```text
Workdir::read
   ↓
raw file validation
   ↓
line model 생성
   ↓
file-context hooks
   ↓
range / limit 적용
   ↓
FileContext
```

이 operation은 `Operations` method로 노출한다.

```rust
operations.build_file_context(request).await
```

`Registry`나 `Workdir`는 인자로 전달하지 않는다. operation이 `Weak<SessionRuntime>`를 통해 얻는다.

## 7.2 FileContext model 추가

예상 모델:

```rust
pub struct FileContext {
    pub path: PathBuf,
    pub byte_len: usize,
    pub total_lines: usize,
    pub lines: Vec<FileContextLine>,
}

pub struct FileContextLine {
    pub line_number: usize,
    pub text: String,
    pub display_prefix: String,
}
```

기본 `display_prefix`:

```text
12
```

hashline 적용 후:

```text
12:abc
```

그러면 renderer는 hashline의 존재를 알 필요가 없다.

```rust
format!("{}|{}", line.display_prefix, line.text)
```

## 7.3 BuildFileContextRequest

예:

```rust
pub struct BuildFileContextRequest {
    pub path: PathBuf,
    pub start_line: Option<usize>,
    pub end_line: Option<usize>,
    pub max_lines: Option<usize>,
    pub max_bytes: Option<usize>,
}
```

필요하면 range type을 별도 model로 분리한다.

## 7.4 validation 책임 이동

`read`에서 하던 다음 로직을 operation으로 이동한다.

- file read
- UTF-8 validation
- NUL / binary rejection
- total line count
- line range validation
- max line handling
- max byte handling

`read` tool은 input parse + operation 호출 + rendering만 담당하게 한다.

## 7.5 hook 실행 시점

hashline은 주변 line context를 해시에 사용할 수 있으므로 **요청 range를 자르기 전에 전체 source를 기준으로 hook augmentation을 수행**한다.

```text
전체 source read
   ↓
전체 FileContextLine 생성
   ↓
BuildFileContextHook
   ↓
requested range slicing
```

range slice 후 hash를 생성하면 파일 전체 기준 tag와 달라질 수 있으므로 금지한다.

# 8. Phase 5 — BuildFileContextHook 및 hashline migration

## 8.1 새 hook 추가

`src/core/hooks.rs`에 새 hook을 정의한다.

예:

```rust
pub struct BuildFileContextHookContext {
    pub path: PathBuf,
    pub source: Arc<str>,
}

#[async_trait]
pub trait BuildFileContextHook: Send + Sync {
    async fn augment_file_context(
        &self,
        context: BuildFileContextHookContext,
        file_context: &mut FileContext,
    ) -> Result<()>;
}
```

`HookRegistry`, `RegisterHook`, `Registry::hooks()` snapshot에 연결한다.

## 8.2 hook 책임 제한

hook은 파일을 직접 읽지 않는다.

잘못된 구조:

```text
HashlineHook
  └─ workdir.read
```

목표 구조:

```text
build_file_context
  ├─ workdir.read
  ├─ FileContext 생성
  └─ hooks
       └─ HashlineFileContextHook
```

## 8.3 HashlineFileContextHook 구현

`tool.enable_hashline`이 켜졌을 때 등록한다.

```rust
struct HashlineFileContextHook;
```

기존 hashline utility를 재사용하고 각 `FileContextLine.display_prefix`만 변경한다.

예:

```text
12      → 12:abc
13      → 13:def
```

hashline algorithm 자체는 변경하지 않는다.

## 8.4 config 동작

`tool.enable_hashline = false`

- hashline hook 등록 안 함
- `patch_hashline` 등록 안 함
- file context 기본 prefix 사용

`tool.enable_hashline = true`

- `HashlineFileContextHook` 등록
- `patch_hashline` 등록
- `read` / `grep`은 코드 변경 없이 hashline 형식 출력

# 9. Phase 6 — read tool migration

## 9.1 직접 Workdir 접근 제거

`tool_read`에서 다음 로직을 제거한다.

- 직접 `workdir.read()`
- 직접 UTF-8/NUL validation
- 직접 hashline rendering
- `enable_hashline` 실행 분기
- 직접 range slicing

새 실행 흐름:

```text
ReadInput deserialize
   ↓
operations.build_file_context(...)
   ↓
FileContext rendering
   ↓
ToolOutput
```

## 9.2 hashline-independent rendering

항상 동일 renderer를 사용한다.

```rust
line => format!("{}|{}", line.display_prefix, line.text)
```

출력:

```text
hashline off: 12|content
hashline on : 12:abc|content
```

## 9.3 description 정책

실행 로직은 hashline 여부를 모르도록 한다.

다만 모델에게 출력 format을 설명해야 하므로 tool definition 생성 시 config에 따른 description variant를 선택하는 것은 허용한다.

즉:

```text
runtime execution policy → build_file_context hook
model-facing documentation → registration/config 시점
```

으로 분리한다.

# 10. Phase 7 — grep tool migration

## 10.1 grep 검색과 파일 표시를 분리

`rg --json`은 match 위치를 찾는 역할만 한다.

```text
rg
 ↓
(path, line_number, match metadata)
```

실제 표시할 line은 `build_file_context`에서 얻는다.

## 10.2 path별 grouping

match마다 file context operation을 호출하지 않는다.

예:

```text
foo.rs:12
foo.rs:18
foo.rs:25
```

이면:

```text
foo.rs → range 12..25
```

로 묶어 한 번만 호출한다.

```rust
operations.build_file_context(...).await
```

이후 line number로 필요한 match를 lookup한다.

## 10.3 기존 hashline cache 제거

다음 종류의 로직을 제거한다.

- `enable_hashline`
- hashline 전용 file cache
- file 재-read
- 직접 `hashline::render()`

최종 renderer:

```rust
format!("{}:{}|{}", path.display(), line.display_prefix, line.text)
```

출력:

```text
hashline off: src/foo.rs:12|content
hashline on : src/foo.rs:12:abc|content
```

# 11. Phase 8 — ToolInputDefinition freeform 구조 개선

## 11.1 새 definition

현재 freeform parser만 optional로 들고 있는 구조를 description까지 한 묶음으로 바꾼다.

```rust
pub struct ToolFreeformDefinition {

pub struct ToolInputDefinition {

    pub freeform: Option<ToolFreeformDefinition>,
```

## 11.2 API 변경

기존:

```rust

```

변경:

```rust
.with_freeform(description, parser)
```

이 구조는 다음 잘못된 상태를 방지한다.

- parser는 있는데 description 없음
- description은 있는데 parser 없음

## 11.3 parse_freeform migration

```rust
self.freeform
    .as_ref()
    .ok_or(...)?.parser
```

형태로 변경한다.

기존 `freeform_parser` 직접 접근 call site를 모두 migration한다.

# 13. Phase 10 — write freeform 단순화

## 13.1 새 format

freeform write 입력은 다음 형식으로 고정한다.

```text
path/to/file
file contents start here
and continue here
```

규칙:

- 첫 번째 줄 전체가 `path`
- 첫 `\n` 뒤의 모든 문자열이 `content`
- content는 빈 문자열 허용
- path는 빈 문자열 금지
- 별도 escaping 없음
- 별도 quoting 없음
- heredoc 없음
- CRLF 입력에서는 path 끝의 `\r`만 제거
- content는 가능한 한 그대로 보존

## 13.2 parser

개념적으로 다음 정도만 필요하다.

```rust
fn parse_write_freeform(input: &str) -> Result<Value> {
    let (path, content) = input
        .split_once('\n')
        .ok_or_else(|| Error::Tool("write freeform input requires a path line".into()))?;

    let path = path.strip_suffix('\r').unwrap_or(path);

    if path.is_empty() {
        return Err(Error::Tool("write path must not be empty".into()));
    }

    serde_json::to_value(WriteInput {
        path: path.into(),
        content: content.into(),
    })
    .map_err(Into::into)
}
```

기존 `WRITE ... <<<TAG` heredoc parser와 관련 prompt/test는 제거한다.

# 14. Phase 11 — typed tool input / json_schema 정리

이번에 건드리는 tool부터 `Value` manual extraction을 제거한다.

기본 패턴:

```rust
#[derive(Debug, Deserialize, JsonSchema)]
struct SomeToolInput {
    ...
}
```

schema:

```rust

```

runtime:

```rust
let input: SomeToolInput = serde_json::from_value(input)
    .map_err(|error| Error::Tool(format!("invalid input: {error}")))?;
```

즉 동일 Rust type이 다음 두 역할을 한다.

```text
Rust Input Type
   ├─ JsonSchema  ──▶ provider schema
   └─ Deserialize ◀── actual JSON input
```

이번 migration 대상:

- `read`
- `grep`
- `write`
- `patch_hashline`

전 repository의 모든 tool을 한 번에 migration할 필요는 없다.

# 16. Phase 13 — patch_hashline schema를 enum으로 생성

## 16.1 loose single schema 제거

하나의 object에 operation별 field를 optional하게 몰아넣는 구조를 제거한다.

피해야 할 구조:

```rust
struct Operation {
    kind: String,
    path: String,
    anchor: Option<String>,
    anchor_start: Option<String>,
    anchor_end: Option<String>,
    lines: Option<Vec<String>>,
}
```

## 16.2 tagged enum 사용

실제 runtime type 자체를 tagged enum으로 만든다.

예:

```rust
#[derive(Debug, Clone, Deserialize, Serialize, JsonSchema)]
struct PatchHashlineInput {
    operations: Vec<PatchHashlineOperation>,
}

#[derive(Debug, Clone, Deserialize, Serialize, JsonSchema)]
#[serde(tag = "kind", rename_all = "snake_case")]
enum PatchHashlineOperation {
    InsertBefore {
        path: String,
        anchor: String,
        lines: Vec<String>,
    },
    InsertAfter {
        path: String,
        anchor: String,
        lines: Vec<String>,
    },
    Replace {
        path: String,
        anchor_start: String,
        anchor_end: String,
        lines: Vec<String>,
    },
    Delete {
        path: String,
        anchor_start: String,
        anchor_end: String,
    },
}
```

실제 variant 이름과 기존 freeform semantics는 현재 구현과 정확히 맞춰 조정한다.

## 16.3 schema 생성

수동 `json!({...})` schema를 제거한다.

```rust
ToolInputDefinition::new(
    json_schema::<PatchHashlineInput>()
)
```

`schemars`가 enum을 기반으로 variant별 schema를 생성하게 한다.

## 16.4 schema/runtime 타입 분리 금지

다음처럼 schema용 타입과 execution용 타입을 따로 만들지 않는다.

```text
PatchHashlineSchemaOperation
   ↓ conversion
PatchHashlineInternalOperation
```

가능한 한 `PatchHashlineOperation` 자체를 patch planner가 직접 사용한다.

# 17. Phase 14 — patch_hashline JSON conversion logic 제거

현재 `Value`에서 `get`, `as_object`, `as_str`, `as_array` 등을 반복해 operation을 만드는 manual parsing을 제거한다.

JSON mode:

```text
Value
 ↓ serde_json::from_value
PatchHashlineInput
 ↓
patch planning / execution
```

execute 진입부 예:

```rust
let input: PatchHashlineInput = serde_json::from_value(input)
    .map_err(|error| {
        Error::Tool(format!("invalid patch_hashline input: {error}"))
    })?;
```

삭제 후보:

- `parse_json_operation`
- generic property getter helpers
- `OperationKind`가 enum과 중복된다면 제거
- JSON DTO → internal DTO conversion layer

anchor string을 실제 `hashline::Anchor`로 validation/parsing하는 것은 domain validation이므로 patch preparation 단계에 남겨도 된다.

# 18. Phase 15 — patch_hashline freeform parser와 typed enum 통합

freeform parser도 같은 `PatchHashlineOperation` enum을 사용한다.

목표:

```text
freeform text
   ↓ DSL parser
PatchHashlineInput
   ↓ serde_json::to_value
ToolInput(Value)
   ↓ common execute path
serde_json::from_value
   ↓
PatchHashlineInput
```

현재 tool abstraction이 freeform parser에서 `Value`를 요구하므로 마지막 JSON round-trip 하나는 허용한다.

하지만 operation별 별도 `operation_to_json()` / `parse_json_operation()` 왕복은 제거한다.

장기적으로 typed `ToolInput`이 도입되기 전까지는 이 구조를 유지한다.

# 21. 테스트 계획

## 21.1 SessionRuntime / lifetime

- SessionHandle 생성 시 runtime이 정상 초기화됨
- `Operations` clone이 runtime lifetime을 강제로 연장하지 않음
- live SessionHandle 또는 TurnEngine이 있으면 runtime이 유지됨
- runtime drop 후 Operations 호출 시 명확한 error 반환
- shutdown이 actor/task를 정상 종료
- store 사용/미사용 session 모두 정상 동작
- layered Workdir이 기존과 같은 순서로 적용됨

## 21.2 TurnEngine

- provider lookup 정상
- hook 호출 순서 유지
- tool execution 정상
- event emission 유지
- session state commit 유지
- cancellation behavior 유지
- 기존 context contribution 동작 유지

## 21.3 build_file_context

- 정상 UTF-8 파일
- empty file
- trailing newline 있음/없음
- invalid UTF-8
- binary/NUL file
- start/end range
- invalid range
- max lines
- max bytes
- line numbering
- hook 없는 기본 prefix
- multiple hooks의 deterministic order

## 21.4 hashline

- enable_hashline off → `line|content`
- enable_hashline on → `line:hash|content`
- read/grep에서 동일 파일/동일 line의 hash가 동일
- 요청 range가 한 줄이어도 전체 파일을 직접 hash한 tag와 동일
- surrounding line 변경 시 contextual hash가 기존 algorithm과 동일하게 변화
- stale anchor behavior 유지

## 21.5 grep

- single-file match
- multi-file match
- 한 파일의 여러 match가 file context 1회로 묶임
- output order 기존 semantics 유지
- hashline on/off output
- 검색 결과 line과 file context line이 정확히 대응

## 21.6 freeform definition/provider

- JSON mode → JSON description 사용
- JSON mode → schema 포함
- freeform mode → freeform description 사용
- freeform mode → custom tool 사용
- freeform parser 없는 tool은 function tool 유지
- custom tool response reconstruction 정상

## 21.7 write freeform

- `path\ncontent`
- multiline content
- empty content: `path\n`
- path with spaces
- CRLF first line
- content 내부 `<<<TAG`, JSON, arbitrary text가 그대로 보존
- newline 없는 입력은 실패
- empty path 실패

## 21.8 patch_hashline schema/input

각 enum variant마다:

- valid JSON deserialize
- required field 누락 실패
- 다른 variant field 조합 실패 또는 무시 여부를 schema/serde 정책에 맞게 명확화
- generated schema에 operation별 variant가 분리됨
- operations 최소 개수 constraint

추가:

- JSON input과 freeform input이 동일한 `PatchHashlineInput` 의미 생성
- replace/insert/delete 동작 기존 regression 유지
- stale anchor failure 유지
- multi-file/multi-operation behavior 유지

# 22. 완료 조건 / Acceptance Criteria

다음 조건을 모두 만족하면 작업 완료로 본다.

### Runtime architecture

- `SessionHandle`이 `Arc<SessionRuntime>` 중심 구조가 됨
- `SessionRuntime`이 registry/workdir/session actor/store/events의 runtime ownership root가 됨
- `Operations`가 `Weak<SessionRuntime>`만으로 필요한 runtime resource에 접근함
- `TurnEngine`이 `Arc<SessionRuntime>` 하나만 핵심 dependency로 가짐
- `TurnEngine::new(registry, operations, workdir)` 형태가 제거됨

### File context/hashline

- `build_file_context` operation 존재
- read/grep이 직접 hashline을 생성하지 않음
- hashline은 BuildFileContext hook으로만 file display를 augment함
- read/grep의 hashline output이 동일 source 기준으로 일관됨
- raw Workdir API와 model-facing file context API의 책임이 분리됨

### Freeform

- JSON/freeform description을 서로 다르게 지정 가능
- provider가 실제 selected input mode에 맞는 description을 사용
- write freeform은 첫 줄 path + 이후 content 형식

### Schema/JSON

- patch_hashline schema가 `json_schema<T>()`에서 생성됨
- patch_hashline operation이 tagged enum으로 표현됨
- 하나의 giant loose object schema가 제거됨
- manual `Value` property parsing/conversion logic이 제거됨
- schema type과 runtime type이 동일 source of truth를 사용함

### Quality

- 기존 주요 runtime/tool tests 통과
- 신규 lifecycle/file-context/freeform/schema regression tests 추가
- compiler warning/dead code 없음
- hashline off 기본 동작에 불필요한 성능 회귀 없음

# 24. 최종 형태 요약

```text
                         Core
                          │
                          ▼
                   SessionHandle
                          │ Arc
                          ▼
                   SessionRuntime
          ┌───────────────┼────────────────┐
          │               │                │
       Registry        Workdir       Session actor/store
          │               │                │
          └───────────────┼────────────────┘
                          │
              ┌───────────┴───────────┐
              ▼                       ▼
         Operations              TurnEngine
       Weak<Runtime>             Arc<Runtime>
              │                       │
              │                       └─ provider/tool/hooks
              │
              └─ build_file_context
                        │
                        ├─ Workdir::read
                        ├─ FileContext 생성
                        └─ BuildFileContextHook
                                  │
                                  └─ HashlineFileContextHook

read ────────────────────────▶ build_file_context

grep ── rg matches ─────────▶ build_file_context


ToolDefinition
  ├─ description                  # JSON/function mode
  └─ ToolInputDefinition
       ├─ schema                  # json_schema<T>()

```

이번 변경의 가장 중요한 결과는 `SessionRuntime`이 세션 실행 context의 단일 루트가 되어 **operation 호출부가 dependency plumbing을 신경 쓰지 않게 되는 것**이다. 그 위에서 `build_file_context`처럼 Registry hook과 Workdir을 동시에 필요로 하는 operation을 자연스럽게 추가할 수 있고, hashline 역시 특정 tool에 흩어진 조건문이 아니라 file-context augmentation이라는 독립된 plugin 기능으로 정리된다.
